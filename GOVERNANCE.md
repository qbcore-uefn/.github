# QBCore UEFN governance

This document explains how organization-wide decisions are made and how work
may be delegated across the QBCore UEFN project.

## Project Owner

[GhzGarage](https://github.com/GhzGarage) is the Project Owner and holds sole
final authority over QBCore UEFN project direction and governance.

The Project Owner may:

- Set or change project priorities, technical direction, and policies
- Appoint, remove, or change the responsibilities of maintainers and community
  moderators
- Approve or reject contributions, releases, organization-wide changes, and
  breaking changes
- Grant or revoke repository, organization, infrastructure, and community
  access
- Resolve disputes and overrule or revisit delegated decisions
- Delegate defined responsibilities without transferring final authority

## Maintainers

Maintainers are trusted contributors appointed by the Project Owner. Within the
scope delegated to them, maintainers may:

- Triage issues and review pull requests
- Request changes and close invalid, duplicate, unsupported, or out-of-scope
  reports
- Merge acceptable changes and maintain repository documentation
- Coordinate releases and migrations when authorized
- Help enforce contribution, security, and community policies

Maintainer authority is delegated and may be changed or withdrawn by the
Project Owner. Maintainers should disclose conflicts of interest and recuse
themselves when they cannot review a matter impartially.

## Community moderators

The official QBCore Discord staff team serves as the community moderation team.
Moderators receive and investigate Code of Conduct reports, protect community
spaces, and apply proportionate moderation measures. A moderator named in a
report must recuse themselves from that report.

Moderators may take immediate protective action when necessary. Organization or
repository access changes that require owner permissions are escalated to the
Project Owner. Reports involving the Project Owner are handled by uninvolved
senior Discord staff under the conflict process in the Code of Conduct.

## Contributors and community members

Anyone may report defects, propose improvements, improve documentation, review
public work, or submit a pull request. Participation does not grant decision or
merge authority. Contributors are expected to follow the contribution guide,
security policy, and Code of Conduct.

## Decision process

Routine repository decisions may be made by maintainers acting within their
delegated responsibility. Significant features, architectural changes,
breaking changes, and organization-wide policies should normally be proposed in
a public issue or pull request so affected community members can provide input.

Consensus is preferred because it improves decisions and long-term support, but
QBCore UEFN is not governed by community vote. When consensus cannot be
reached, or when the Project Owner determines that a different outcome better
serves the project, the Project Owner makes the final decision.

Security vulnerabilities, Code of Conduct reports, credentials, personal data,
and other sensitive matters are handled privately. Public summaries may be
provided after resolution when doing so is safe and useful.

## Changes to governance

Governance changes may be proposed through a pull request to the organization's
`.github` repository. A governance change takes effect only after approval by
the Project Owner.
